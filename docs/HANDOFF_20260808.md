## 아키텍처 핵심 패턴

이전 인수인계서(`HANDOFF_20260807.md`)의 패턴은 모두 유효하다. 이번 세션에서 추가/변경된 것만 기록한다.

- **`(app)` 라우트 그룹 = 인증 필요 영역**: `src/app/(app)/`에 있는 모든 페이지는 `layout.tsx`가 인증 확인 + 헤더를 감싼다. 새 인증 필요 페이지는 반드시 이 그룹 안에 만들 것(URL엔 영향 없음). `login`/`signup`/`invite`/`auth/callback`/`reset-password`는 그룹 밖(공개).
- **활성 회사 = `active_org_id` httpOnly 쿠키**: `src/lib/org/active-organization.ts`의 `getAccessibleOrganizations`/`resolveActiveOrgId`를 재사용할 것. 새로 만드는 페이지가 "현재 선택된 회사" 개념이 필요하면 이 두 함수를 그대로 쓴다(중복 구현 금지).
- **`is_org_member`/`is_org_admin` 딱 두 함수가 전체 권한의 단일 지점**: 멤버십 관련 새 조건(이번 세션의 `status='active'`)을 추가할 땐 이 두 함수만 고치면 RLS·모든 Server Action의 권한 체크에 자동 반영된다. 단, **RLS SELECT 정책에 이 함수를 쓰는 테이블은, 그 조건에 안 걸리는 사람이 "자기 자신의 관련 행"조차 못 보게 되는 부작용이 생길 수 있다** — 이번에 `organization_members`/`organizations`에 별도의 "본인 것은 항상 보임" 정책을 추가로 넣어야 했다. 앞으로 비슷한 조건을 추가할 때 이 패턴을 먼저 점검할 것.
- **Service Role 클라이언트는 `src/lib/supabase/admin.ts`를 통해서만**: `SUPABASE_SERVICE_ROLE_KEY`는 Server Action 안에서만 사용하고, 호출 전 반드시 일반 클라이언트로 `is_platform_admin()`을 먼저 확인한다(`src/app/(app)/admin/actions.ts`의 `requirePlatformAdmin()` 패턴 재사용). 클라이언트 컴포넌트에서 이 모듈을 import하면 안 됨.
- **회사 프로필도 JD 버전처럼 "수정 = 새 버전"**: `organization_profiles`는 기존 행을 덮어쓰지 않고 `version_no+1`로 추가한다. 회사 정보를 쓰는 새 기능은 항상 **조직의 최신 버전**을 조회해야 한다(v1.1 리팩터 전에는 고정된 옛 버전을 쓰는 버그가 있었다).
- **관리자 화면 스타일은 `src/components/admin/ui.ts` 토큰만 사용**: 새 관리자 UI를 추가할 때 임의로 색상·여백을 정하지 말고 이 파일의 `adminCardClass`/`adminButtonClass`/`adminInputClass`를 재사용할 것.
- **단일 소속 모델**: 한 사용자는 항상 한 회사에만 속한다(DB 자체는 여러 행을 허용하지만, 앱 로직/UI는 "변경 = 기존 삭제 후 새로 추가"로 취급). 이 전제를 깨는 기능(한 사람이 여러 회사에 동시 소속)을 추가하려면 `changeUserOrganization`과 `MembersPanel`의 단일-멤버십 가정을 다시 설계해야 한다.

- 회원 삭제(`deleteUserAccount`)는 되돌릴 수 없다. UI에서 이메일 재입력 확인을 이미 넣어뒀지만, 이 로직을 수정할 땐 확인 절차를 약화시키지 말 것.
- `changeUserOrganization`은 대상 사용자의 기존 `organization_members` 행을 **전부 delete**한다(단일 소속 가정). 다중 소속을 지원하게 되면 이 함수부터 고쳐야 한다.
- 관리자 화면 새 UI는 `src/components/admin/ui.ts` 토큰을 임의로 우회하지 말 것 — 우회하면 이번에 통일한 스타일이 다시 흩어진다.
- 사용자 또는 다른 에이전트의 변경이 작업 트리에 섞여 있으면 `/인계` 커밋 전에 diff로 범위를 확인한다.
