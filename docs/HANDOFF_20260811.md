## 아키텍처 핵심 패턴

- **제품 원칙**: 회사 소개 자료/입력과 최소한의 팀 정보로 Gemini가 NCS 근거를 연결해 JD v1.0을 만든다. 사용자는 선택적 정보를 보완해 v1.1을 만들며, NCS 근거가 검토 루프로 다시 작동해야 한다.
- **인증/조직 컨텍스트는 `src/lib/auth/session.ts` 경유**: `getSessionUser()`/`getOrgContext()`는 React `cache()`로 감싸져 있어 같은 요청 안에서 몇 번을 불러도 Supabase 왕복은 1번이다. 페이지에서 `supabase.auth.getUser()`를 직접 호출하거나 `getAccessibleOrganizations`를 다시 부르지 말고 이 모듈을 경유한다.
- **권한 판단은 이제 진짜로 role을 본다**: `is_org_member(orgId)`는 "조회 가능"(소속만 있으면 member든 admin이든), `is_org_admin(orgId)`는 "쓰기 가능"(role이 owner/admin이거나 플랫폼 운영자)이다. 회사 프로필/JD/팀 관련 새 기능을 추가할 때 RLS insert/update/delete 정책은 `is_org_admin`을 써야 한다 — `is_org_member`를 쓰면 예전처럼 일반 사용자도 쓸 수 있게 된다.
- **`memberRole`을 UI에서 실제로 쓴다**: `getAccessibleOrganizations`가 반환하는 각 조직의 `memberRole`("super_admin"|"owner"|"admin"|"member")로 `canManage = memberRole !== "member"`를 판단해 쓰기 UI를 감춘다. 새 쓰기 기능을 만들 때 이 패턴을 재사용한다(참고: `src/app/(app)/page.tsx`, `src/app/(app)/company/page.tsx`, `src/app/(app)/jobs/new/page.tsx`, `src/app/(app)/jobs/[id]/edit/page.tsx`).
- **서버 액션은 RLS와 별개로 명시적 권한 체크를 한다**: RLS가 최종 방어선이지만, 사용자에게 원문 Postgres 오류 대신 한국어 안내를 주기 위해 서버 액션 초입에서 `is_org_admin`/`is_org_member` RPC를 명시적으로 호출한다.
- **DB 스키마 변경 검증은 impersonation으로**: `execute_sql`에서 `select set_config('request.jwt.claims', '{"sub":"<user_id>","role":"authenticated"}', true); set local role authenticated;` 뒤에 실제 쿼리를 실행하면 특정 사용자로 가장해 RLS가 진짜 막는지/뚫는지 확인할 수 있다. 이번 세션에 여러 번 이 방법으로 "코드만 보고 맞다고 가정"하지 않고 직접 검증했다 — 테스트 후에는 반드시 테스트 데이터/역할 변경을 원복한다.
- **JD 상태 흐름**: `team_roles.status`는 `jd_status` enum(`draft`|`in_review`|`approved`|`archived`)이며 "확정" UI는 `approved`로 매핑한다.
- **JD 삭제는 cascade**: `team_roles` 삭제 시 `jd_versions → jd_sections → jd_evidence`, `role_ncs_mappings`, `jd_validation_runs`까지 FK cascade로 정리된다.
- **관리자 화면은 회사별 테이블이 기본 단위**: `company-members-panel.tsx`가 조직별로 테이블을 그린다. 새 관리 기능을 추가할 때 예전처럼 평면 회원 목록으로 되돌리지 않는다.
- **플랫폼 운영자는 회사에 소속되지 않는다**: `organization_members`에 절대 행을 만들지 않는다. `changeUserOrganization`이 이를 서버에서 막고 있으니 우회하는 새 코드를 만들지 않는다.
- **공용 페이지 레이아웃**: 로그인 후 모든 페이지는 `src/components/layout/page-container.tsx` + `page-header.tsx`를 쓴다. 히어로(`bg-slate-950`) 스타일은 대시보드·JD 리포트에만.
- **Service Role 격리**: `SUPABASE_SERVICE_ROLE_KEY`는 `src/lib/supabase/admin.ts` 등 서버 전용 코드에서만 사용한다.
- **검증 후 배포**: `npx tsc --noEmit`, `npm run lint`, `npm run build`, `npm test`를 통과한 변경만 `master`에 푸시한다. DB 변경은 Supabase MCP `apply_migration`으로 즉시 프로덕션에 반영하고 같은 SQL을 `supabase/migrations/`에도 커밋한다.

## 미해결 과제

1. **오늘 배포한 기능들의 실사용 검증 (최우선)**
   - 관리자 콘솔 재구성(회사별 테이블, 초대 링크 복사, 역할 드롭다운)을 실제 관리자 계정으로.
   - `일반` 역할 계정으로 로그인해 회사 프로필 읽기 전용 뷰, JD 생성/보완 안내 문구, 대시보드 버튼 숨김이 실제로 예상대로 보이는지.
   - `관리자` 역할 계정으로는 기존처럼 전부 쓸 수 있는지.
   - 새로 만드는 JD의 Evidence coverage 점수가 이제 92~95 좁은 대역이 아니라 실제로 갈리는지.

2. **가입 요청 UX 보완**
   - 거절된 사용자의 재신청 상태와 사유 표시, 승인 대기 화면 개선 여지.

3. **제품 고도화 잔여 과제**
   - 문체 가이드/MVC 반영 엔진, NCS 검색 정확도, 버전 이력 UI, 오래된 JD 정리 정책(현재는 수동 삭제만), PDF 자동 테스트, Sentry 활성화, npm audit 취약점 검토.

4. **Vercel 프로젝트/도메인 이름 잔여 정리 (선택)**
   - 원한다면 `ncs-jd-operator.vercel.app`을 Vercel Domains에서 제거하거나 새 도메인으로 리디렉션 가능(현재 둘 다 활성 유지, 강제 조치 아님).

## 주의사항

- `.env.local`, Supabase/Gemini/NCS/Sentry 키, `SUPABASE_SERVICE_ROLE_KEY`, DB 비밀번호, Vercel 토큰/브라우저 로그인 정보는 절대 커밋하지 않는다.
- **회사 프로필/JD/팀 관련 테이블에 새 RLS 정책을 추가할 때 `is_org_member`를 insert/update/delete에 쓰지 않는다** — 그러면 `일반` 역할도 다시 쓸 수 있게 되어 이번 세션에 고친 걸 되돌리는 셈이다. 쓰기는 `is_org_admin`, 조회만 `is_org_member`.
- **DB 스키마·RLS를 바꿀 때는 코드만 보고 판단하지 말고 impersonation으로 직접 검증한다.** `list_all_organization_members()`/`list_pending_access_requests()`가 배포 이후 한 번도 정상 동작한 적이 없었는데도 아무도 몰랐던 이유가 "호출부가 에러를 삼키고 빈 배열로 처리"했기 때문이다 — 에러를 삼키는 코드 근처의 기능은 특히 의심할 것.
- **플랫폼 운영자에게 `organization_members` 행을 만들지 않는다.** `changeUserOrganization`이 막고 있지만, 다른 경로(SQL 직접 실행 등)로 우회하지 않는다.
- Vercel CLI는 로그아웃 상태다. 토큰을 코드나 셸 기록에 직접 적지 말 것.
- 도메인을 바꿀 때는 Supabase 인증 Redirect URL을 함께 계획한다.
- 공식 로고는 제공된 PDF/AI에서 추출한 저장소 자산을 사용한다. CSS/HTML 텍스트로 워드마크를 다시 만들지 않는다.
- `src/lib/supabase/admin.ts`를 클라이언트 코드에서 import하지 않는다.
- `deleteUserAccount`, `deleteRole`은 되돌릴 수 없는 작업이다.
- 로그인 후 페이지를 새로 만들 때는 `PageContainer`/`PageHeader`를 재사용한다.
- Claude in Chrome 브라우저 확장 연결이 세션 중간에 끊길 수 있다(관측됨). 끊기면 재시도하거나 대체 수단(직접 확인 요청 등)이 필요하다.
- 작업 트리에 다른 사용자의 변경이 있으면 덮어쓰지 말고 diff로 범위를 확인한다.
