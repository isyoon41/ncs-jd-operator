## 아키텍처 핵심 패턴

- **회사 우선 설계**: 회사 소개/IR → `organization_profile` → 팀 설계 → 대표 JD 순서다. NCS가 회사를 덮어쓰지 않고 회사 현실을 보완하는 근거로 작동한다.
- **사용자 최소 입력**: v1.0 생성에 필수인 사용자 입력은 회사 맥락, 팀명, 팀 역할이다. 사용자가 NCS 능력단위를 직접 선택하지 않는다.
- **NCS 화이트리스트**: Gemini는 DB에서 조회한 후보 코드만 사용할 수 있다. `normalizeDesign`이 허용 목록에 없는 코드를 제거한다. 적합한 NCS가 없으면 빈 매핑을 허용한다.
- **두 단계 AI 루프**: 직무설계 생성과 독립 검토를 분리한다. 검토 단계가 수정된 완성본, coverage 점수, findings를 반환한다.
- **Gemini 복합 출력 방식**: 깊은 중첩 객체는 `encodedPayloadSchema`의 `payload` 문자열로 전달한 뒤 서버에서 `JSON.parse`와 정규화를 수행한다. 복잡한 `responseSchema`로 되돌리면 Gemini 3.6 Flash에서 400 오류가 재발할 수 있다.
- **문장별 근거**: 책임/자격요건별로 실제 NCS 코드와 회사·팀 입력 출처를 저장한다. 과거의 Cartesian 매핑을 다시 사용하지 않는다.
- **불변 기준본**: v1.0과 v1.1은 각각 `design_snapshot`을 보존한다. 현재 UI는 최신 버전만 보여주며 v1.1 생성 후 추가 minor 버전은 막는다.
- **멀티테넌시**: 일반 사용자는 `organization_members`와 RLS로 자기 조직에 격리된다. 플랫폼 관리자는 별도 정책과 `is_platform_admin()`을 통해 모든 조직에 접근한다.
- **서버 전용 키**: Gemini 호출은 Server Action/`server-only` 모듈에서만 수행한다. `GEMINI_API_KEY`에 `NEXT_PUBLIC_` 접두사를 붙이지 않는다.
- **Supabase 클라이언트 분리**: 브라우저 `client.ts`, 서버 `server.ts`, 세션 갱신 `middleware.ts`를 구분한다.
- **NCS 데이터 전략**: 불안정한 공공 API를 런타임에서 직접 호출하지 않고 Supabase에 적재된 기준 데이터를 내부 조회한다.
- **Next.js 16 규칙**: 코드 변경 전 `node_modules/next/dist/docs/`의 관련 가이드를 읽는다. Server Action 업로드 한도는 `next.config.ts`에서 11MB이며 실제 파일 검증은 8MB다.
- **Git 규칙**: 일반 커밋은 사용자가 요청할 때만 한다. `/인계`는 문서 작성, 비밀값 확인, 커밋, `origin` 푸시까지의 명시적 요청이다.

3. **실제 IR PDF 통합 테스트**: PDF inline Gemini 처리와 private Storage 코드는 구현했지만 이번 E2E는 직접 입력한 회사 소개로 수행했다. 실제 퓨리오젠 IR/회사소개 PDF로 8MB 이하 업로드를 검증해야 한다.
4. **NCS 검색 품질 고도화**: 현재 검색은 Gemini가 만든 구체 검색어를 `ncs_competency_units.name ILIKE`로 조회하고 대분류 코드로 거른다. 임베딩/전문검색, 정의·분류 데이터 보강, 동의어 사전을 추가하면 누락과 편향을 줄일 수 있다.
5. **NCS 상세 데이터 보강**: 초기 13,442건의 핵심은 코드·명칭·레벨이다. 정의와 대·중·소·세분류가 비어 있는 행을 라이선스가 명확한 데이터로 보강해야 한다.
6. **버전 이력 UI**: v1.0 스냅샷은 DB에 보존되지만 v1.1 생성 후 화면에서 과거 v1.0을 선택해 비교하는 UI는 없다. 버전 비교/복원 기능을 설계할 수 있다.

8. **여러 직무·기업 검증**: 퓨리오젠 BD 한 사례 외에 연구개발, 생산, 품질, 지원부서와 다른 산업 회사로 NCS 충돌 방지 성능을 검증해야 한다.

## 주의사항

- `.env.local`, 실제 Gemini/Supabase/NCS 키, DB 비밀번호, CLI 자격증명은 절대 커밋하지 않는다.
- 저장소는 Public이다. 서비스 로직 공개 범위가 커지면 Private 전환 여부를 다시 판단한다.
- 복잡한 `teamDesignSchema`/`validationSchema`를 Gemini `responseSchema`에 직접 넣으면 `400 INVALID_ARGUMENT`가 재발했다. 현재 `encodedPayloadSchema`를 변경할 때는 실제 Gemini E2E를 반드시 재실행한다.
- Server Action에서 `redirect()`를 `try/catch` 안에 두면 Next.js redirect 예외를 사용자 오류로 잡을 수 있다. 현재처럼 저장 로직이 끝난 뒤 catch 밖에서 호출한다.
- 회사 파일은 PDF/TXT/MD, 최대 8MB다. Storage bucket은 private이고 Next Server Action body limit은 11MB다.
- v1.1 Server Action은 최신 버전이 이미 v1.1이면 추가 생성을 거부한다. 버전 정책을 확장할 때 UI, Action, `version_major/minor`를 함께 수정한다.
- 원격 DB 스키마 변경은 적용되어 있지만 마이그레이션 이력 정합성을 확인하기 전 무심코 `db push`하지 않는다.
- 레거시 JD의 과거 `jd_evidence`에는 모든 책임에 모든 NCS가 연결된 데이터가 남아 있다. 화면에서 숨기고 있을 뿐이므로 통계나 내보내기 구현 시 레거시 여부(`organization_profile_id`와 validation 존재)를 반드시 판별한다.
- 퓨리오젠 회사 프로필 v1은 기존 Technical BD에 사용자가 입력했던 사실을 바탕으로 통합 테스트 중 생성한 데이터다. 실제 IR 자료가 제공되면 새 프로필 버전으로 갱신한다.
- `database.types.ts`는 새 스키마에 맞게 수동 갱신했다. 이후 Supabase CLI로 타입을 재생성하면 커스텀 변경이 사라질 수 있으니 diff를 검토한다.
- NCS 검색 결과가 없거나 적합하지 않으면 빈 NCS 매핑을 허용하는 것이 정상이다. 무관한 NCS를 억지로 연결하지 않는다.
- 사용자 또는 다른 에이전트의 변경이 작업 트리에 섞여 있으면 `/인계` 커밋 전에 diff로 범위를 확인한다.
